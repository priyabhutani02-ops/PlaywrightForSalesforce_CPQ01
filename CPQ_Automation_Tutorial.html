01 — Overview

What this project is, in one paragraph

This is an automated testing framework for a Salesforce CPQ implementation. CPQ ("Configure, Price, Quote") is the part of Salesforce that turns a sales conversation into a priced quote, then into an order, then into a signed contract — and later lets you amend that contract when the customer changes what they bought. Each of those steps involves many screens, calculations, and approvals. Testing them by hand before every release is slow and easy to get wrong.

Our framework performs those journeys automatically. It logs into Salesforce, creates real test records, drives the CPQ screens, makes the same changes a salesperson would, and then checks that Salesforce actually did the right thing — correct quantities, correct dates, correct documents created. It produces a clean report at the end so anyone can see, at a glance, what passed and what didn't.

In plain terms Think of it as a tireless QA engineer who can run the entire sales-to-contract process hundreds of times overnight, and hand you a tidy report in the morning.
02 — The Value

Why automate this at all

CPQ is high-stakes. A pricing or contract error doesn't just fail a test — it can ship a wrong quote to a real customer. Manual regression testing of CPQ is expensive and inconsistent. Automation changes the economics:

01

Speed

A full amendment journey that takes a person 15–20 minutes runs unattended, many in parallel.

02

Confidence

Every run verifies the actual data in Salesforce, not just that screens "looked fine".

03

Repeatability

The same checks run identically every time — no skipped steps, no human variance.

04

Coverage

Test data lives in a spreadsheet, so adding new scenarios is a new row, not new code.

05

Evidence

Screenshots, videos, logs and an HTML report give an audit trail for every run.

06

Lower cost

QA effort shifts from repetitive clicking to reviewing results and edge cases.

04 — Scope

What the framework currently tests

Four end-to-end journeys are automated, each as its own test scenario:

ScenarioWhat it proves
Quote without approvalA standard deal with a discount inside policy flows cleanly from quote to order to contract.
Quote with approvalA higher discount correctly triggers the approval process, and the deal proceeds only once approved.
Bundle productA configurable bundle (e.g. a laptop with CPU, RAM and storage options) is built and priced correctly.
Amendment (showcase)An existing contract is amended — quantity and start date changed — producing a correct new order and contract.
Designed to grow New scenarios don't require a developer for every case. Because data is read from a spreadsheet, a tester can add a row — different product, quantity, discount or date — and it becomes a new automated test.

The "hybrid" approach — and why it's smart

Driving every single step through the browser would be slow and fragile. Instead, the framework uses two channels:

  • API channel for plumbing — creating the Account, Contact, Opportunity and base Quote, setting quantities and discounts, activating orders. This is fast and stable.
  • UI (browser) channel for the parts that genuinely must be tested through the interface — the Quote Line Editor, the "Amend" buttons, the pricing calculation. This is where real user experience is validated.

The result is a suite that is both fast and realistic — it doesn't waste minutes clicking through forms that an API can fill in seconds, but it never skips the screens a customer actually uses.

Login once, test many

Logging into Salesforce on every test would waste time and hammer the login service. The framework authenticates once at the start of a run, saves that session, and every test reuses it. Authentication uses a secure server-to-server method (JWT) — no passwords are stored in the tests.

06 — Walkthrough

The amendment journey, step by step

This is the flagship scenario. Tags show whether each step runs via the fast API channel or the real browser UI.

Create the customer & quote APIAn Account, Contact, Opportunity and base Quote are created instantly via the API.
Add a product on the Quote screen UIThe Quote Line Editor is opened in the browser, a product is added and prices are calculated — exactly as a salesperson would.
Set the original quantity & discount APIStarting quantity and an in-policy discount are applied.
Win the deal → Order → Contract APIThe opportunity is closed-won, an order is created and activated, and a contract is generated. The framework waits for Salesforce to finish before continuing.
Open the contract and click "Amend" UIThe amendment is started through the real Salesforce screens, which produces a brand-new Amendment Quote.
Change the quantity and start date APIThe amendment quote is updated — for example, quantity goes from 1 to 7, with a new start date — then re-priced.
Verify the amendment is correct APIThe framework reads the data back from Salesforce and asserts the quantity and start date are exactly what was requested.
Order & contract the amendment APIThe amended quote becomes an amended order, is activated, and generates a new amended contract.
Final verification APIThe amended contract's start date is checked. Only if every assertion passes is the test marked green.
The important part Notice the two explicit verify steps. The test doesn't just "do" the journey — it independently confirms Salesforce stored the right numbers. That is the difference between a script and a real test.

08 — Operating Guide

How to run it

For the technical team. Anyone with Node.js installed and Salesforce credentials can run the suite.

One-time setup

# install dependencies and the browser
npm install
npx playwright install chromium

# copy the sample config and fill in your Salesforce details
cp .env.example .env

# generate the sample test-data spreadsheet
npm run data

Everyday commands

npm test              # run everything, headless & in parallel
npm run test:headed   # watch it run in a visible browser (great for demos)
npm run test:amendment# run only the amendment journey
npm run report        # open the HTML report from the last run
Credentials stay private Salesforce keys and the connection file (.env) are never committed to source control. The framework authenticates with a key-based method, so no human password lives in the project.
09 — Results

What you see after a run

Two things every stakeholder cares about: did it pass, and if not, why.

The HTML report

An interactive report lists every scenario as pass or fail. Open any test to see its journey broken into named steps — "Create quote", "Start amendment", "Verify quantity" — each individually marked. The verification steps show the exact expected-vs-actual values, so a failure tells you precisely what Salesforce got wrong.

Evidence on failure

When something fails, the framework automatically attaches a screenshot at the moment of failure, a video of the run, and a trace you can step through. No need to reproduce the issue by hand.

Logs

Each run creates a dated folder under logs/ containing a full activity log and a separate error log — useful for audits and for debugging environment issues.

For dashboards

JSON and JUnit report files are also produced, so results can plug straight into a CI/CD pipeline or a quality dashboard.

10 — Engineering Quality

Why it stays maintainable as it grows

A test suite is only valuable if the team keeps it green and keeps adding to it. Several deliberate choices protect that:

  • Page Object Model. Each Salesforce screen has one dedicated module holding its locators and actions. If Salesforce changes a button, it's fixed in exactly one place.
  • Shared base & utilities. Common waits, navigation, assertions, data and logging are centralised — no copy-pasted logic drifting out of sync.
  • Configuration, not hard-coding. URLs, timeouts, parallelism and demo-vs-CI mode are controlled by simple environment settings.
  • Resilience to timing. Salesforce processes some steps asynchronously; the framework politely waits and retries rather than failing on slow responses.
  • Clean dependencies. Only the libraries actually used are kept, reducing security surface and install time.

Scaling to 100 scenarios

To grow coverage, a tester adds rows to the data spreadsheet and runs the suite with more parallel workers. No new code is required for new data combinations. New types of journey (e.g. renewals, cancellations) reuse the same building blocks already in place.

Roadmap note The Quote and Bundle screen modules can be brought fully in line with the same structured pattern used by the Contract and Amendment modules — a small, well-defined next step that further improves consistency.
